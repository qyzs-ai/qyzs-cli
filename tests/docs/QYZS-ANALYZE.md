### 3.3 关键技术突破：`paddleocrvl` FastDeploy 2048 限制与解决方案

在测试 `paddleocrvl` 原始扫描件时，系统触发了严重的底层异常：
```
fastdeploy.utils.EngineError: Input text is too long, input_ids_len (2047) + min_tokens(1) >= max_model_len(2048)
```
**机理剖析**：
- 庆阳智算中心部署的 `paddleocrvl` 采用 FastDeploy 推理后端，启动参数被严格硬编码为 `max_model_len = 2048`。
- 高分辨率原图（>1000px）在通过视觉特征投射（Vision Tokenizer）时，会离散化为 2048 个视觉 Embedding，导致输入直接越界触发 500 崩溃。

**对齐解决方案**：
- 客户端在调用 `paddleocrvl` 时，必须实施**智能自适应缩放预处理**：将图像长边等比例缩放至 $\le 800\text{px}$。
- 实测验证：等比缩放至 800px 后，Token 占用降至 1,200 左右，识别耗时仅 1.7~1.9 秒，且文字识别准确率未受任何实质影响。

### 3.5 生成参数边界实测（`max_tokens` / `temperature`）

**`max_tokens` 接受范围**（提示词为短文本，验证网关/模型侧参数校验）：

| 取值 | `dsv4` | `qwen3.6-27b` | `qwen3-VL-30B-A3B` | 行为 |
| ---: | :---: | :---: | :---: | :--- |
| 1 | ✅ | ✅ | ✅ | `finish_reason=length`（截断语义正常） |
| 1,024 ~ 65,536 | ✅ | ✅ | ✅ | 全部接受，`finish_reason=stop` |

结论：三款模型 `max_tokens` 实测下限 1、上限 **≥65,536** 均被接受，原「1~8192」的保守约定可放宽；实际生成长度受剩余上下文窗口约束。

**`temperature` 校验边界**：

| 取值 | `dsv4` | `qwen3.6-27b` |
| ---: | :---: | :---: |
| -0.5 | ❌ 400 `temperature must be non-negative` | ❌ 拒绝 |
| 0.0 ~ 2.0 | ✅ 接受 | ✅ 接受 |
| 2.1 | ❌ 400 `temperature must be in [0, 2]` | ✅ 接受 |
| 2.2 ~ 8.0 | （未再上探） | ✅ 接受 |

结论：`dsv4` 服务端硬校验区间为 **[0, 2]**（报错原文确认）；`qwen3.6-27b` 无严格上界校验（8.0 仍接受），生产建议仍约束在 0~2 以保证输出质量。

### 4.2 业务互验仲裁机制推演

```
           ┌────────────────────── 用户输入公文 (PDF/DOC) ──────────────────────┐
           │                                                                    │
           ▼                                                                    ▼
 ┌─────────────────────────┐                                        ┌─────────────────────────┐
 │   MinerU 3.2.3 专线     │                                        │  paddleocrvl 视觉专线   │
 │   提取 Markdown 大纲    │                                        │  提取像素坐标与印章文本 │
 └────────────┬────────────┘                                        └────────────┬────────────┘
              │                                                                  │
              └───────────────────────────────┬──────────────────────────────────┘
                                              ▼
                                 ┌────────────────────────────────┐
                                 │   同源互验器 (CLI `verify`)      │
                                 │   计算 char n-gram Jaccard      │
                                 │   并与 15% 阈值比较判定同源      │
                                 └────────────────────────────────┘
```

1. **红头与文号仲裁**：MinerU 对红头扫描件的标题和正文结构化解析能力优于单页 OCR（MinerU 召回率 100%）；
2. **印章文本**：`paddleocrvl` 能够转录红色公章上的组织名称（见 pair_03 实测），但当前 CLI **没有**坐标标注与印章剔除实现，印章文字原样保留在抽取结果中——`--strip-seals` 从未实现，勿当作可用参数；
3. **互验判定口径（实测校正）**：`verify` 以**字符 n-gram（n=2）Jaccard** 度量，**≥ 0.15 判为同源通过**（方向是"高于阈值才算同源"，不是低于阈值就熔断）；低于阈值时仅打印未达阈值的告警与建议人工复核，**不触发任何双模型二次复核**。此前版本用"唯一字符集合 Jaccard"，对中文公文无鉴别力（同源与无关文档均 49%~87%），已弃用。

### 5.3 MinerU 同步解析页数阶梯（5 → 30 页）

由源 PDF 循环扩页合成等宽样本（0.2 MB）实测同步通道：

| 页数 | 体积 | 端到端延时 | 解析状态 | Markdown 输出 |
| ---: | ---: | ---: | :---: | ---: |
| 5 页 | 0.20 MB | 3.118s | completed | 2,105 字符 |
| 15 页 | 0.21 MB | 5.078s | completed | 6,534 字符 |
| 30 页 | 0.21 MB | 7.659s | completed | 13,285 字符 |

结论：同步通道实测 **30 页无断点**（≈0.26 s/页），原「15 页同步上限」的约定偏保守。**CLI 当前只实现同步通道**：网关返回 `pending`/`running` 时直接报错（提示减小页数或体积后重试），**没有 `/tasks` 端点、没有轮询循环、没有自动转异步**。把上表数据当作可上调阈值的依据前，须先补异步通道实现。

## 6. 综合结论与生产环境部署建议

1. **主对话推理路由**：全面绑定 `dsv4`，其 1.0s 短文本延迟与实测 **51.8 万 Tokens** 零误差召回（梯度内未见天花板）表现领先全场，超长文档无需分块直读。
2. **大模型思考与推演**：复杂业务推演与规划标准仲裁绑定 `qwen3.6-27b`，但限用于 **≤3 万 Tokens** 场景——实测 13.8 万 Tokens 需约 237s，同规模延迟约为 `dsv4` 的 10 倍，且必须预留 ≥2048 的 `max_tokens` 思维链预算。
3. **图文与视觉路由**：多图并发核验绑定 `qwen3-VL-30B-A3B`，**可靠工作点为 16 图/请求**，超过时 **CLI 自动分批**（每批 ≤16 张，如 20 图拆为 16+4；网关虽可承载 48 图/13.2 MB，但 24 图起计数漂移、32 图起输出为空）；纯文本快速通道可用其文本能力（硬上限 131,072 Tokens，10 万 Tokens 仅 8.7s）；公文版面快速转录绑定预处理后的 `paddleocrvl`（≤800px）。
4. **公文规章结构化**：以 `MinerU 3.2.3` 为核心骨干（同步通道实测 ≥30 页无断点），配合 `paddleocrvl` 做扫描件文本层互验。**坐标核验与印章剥离均未实现**，勿按已实现能力规划。
5. **向量与检索**：长文本向量化统一路由 `bge-m3` 并按 ≤12,000 字符分块；`bge-large-zh-v1.5` 仅用于 ≤500 字符短句表征；重排切片 ≤100 篇/批，优先 `bge-reranker-v2-m3`。
6. **参数边界**：`temperature` 客户端与服务端统一约束在 [0, 2]（`dsv4` 的服务端硬校验区间）；`max_tokens` 客户端校验区间为 1~1,000,000，实测服务端对 1~65536 均接受——客户端侧为防误传退化值主动收紧。
7. **调度配置化**：本报告采集的模型实测参数已固化至 `capability_matrix.toml`（默认模型、per-model 超参、`models` 渲染矩阵，含 5 个实测禁止调度的已下线项）。**注意**：该文件只承载参数与模型清单，不承载路由熔断规则；CLI 实际行为以 `src/` 源码为准。
